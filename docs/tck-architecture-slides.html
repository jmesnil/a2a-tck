What is the A2A TCK?

A conformance test suite that validates A2A protocol implementations

Goal

Ensure any A2A SDK correctly implements the protocol specification, regardless of language or framework.

How

Black-box testing: the TCK sends requests over the wire and validates responses against the spec.

Validates across 3 transports

gRPC

Protobuf binary over HTTP/2

JSON-RPC

JSON-RPC 2.0 over HTTP

HTTP+JSON

RESTful HTTP with JSON payloads

4

Requirement Levels (RFC 2119)

Tests are organized by specification conformance level

Level Meaning Test Behavior Example IDs
MUST Absolute requirement Hard failure if not met CORE-SEND-001
SHOULD Expected unless valid reason to differ Expected failure (xfail), does not block CORE-EXECUTION-MODE-001
MAY Truly optional Skipped if agent doesn't declare capability CORE-STREAM-001

Each requirement is a RequirementSpec with: ID, spec section, level, operation type, transport binding, sample input, expected behavior, and validators.

RequirementSpec(
    id="CORE-SEND-001",
    section="3.1.1",
    title="SendMessage returns Task or Message",
    level=RequirementLevel.MUST,
    operation=OperationType.SEND_MESSAGE,
    binding=SEND_MESSAGE_BINDING,
    expected_behavior=
        "Response contains either a Task "
        "object or a Message object",
    sample_input={
        "message": {
            "role": "ROLE_USER",
            "parts": [{"text": "Hello from TCK"}],
            "messageId": tck_id("complete-task"),
        },
    },
)

The Scenario System

Gherkin features define SUT behavior -- no side-channel API needed

Feature: Core Operations

  Scenario: Complete the task
    When a message is received
         with prefix "tck-complete-task"
    Then complete the task
         with the message "Hello from TCK"

  Scenario: Task with text artifact
    When a message is received
         with prefix "tck-artifact-text"
    Then complete the task
    And add an artifact
        with a text part "Generated text"

  Scenario: Task requiring user input
    When a message is received
         with prefix "tck-input-required"
    Then update the task status
         to "input_required"

In-band signaling

The messageId prefix is the signal linking TCK tests to SUT behavior. The SUT matches the prefix and executes the corresponding scenario.

Code generation

The codegen system parses these Gherkin files and generates SUT implementations for multiple SDKs (Java/Quarkus with a2a-java, Python with a2a-python).

Two feature files

  • core_operations.feature -- task lifecycle, artifacts, errors
  • streaming.feature -- streaming events, resubscription

What Your SDK Must Do

To pass the TCK, your agent implementation needs these pieces

1. Agent Card

Serve a valid agent card at:

GET /.well-known/agent-card.json
  • Declare supportedInterfaces with protocol bindings and URLs
  • Declare capabilities: streaming, push notifications, etc.

2. Transport Endpoints

Implement at least one transport:

  • gRPC -- proto service
  • JSON-RPC -- JSON-RPC 2.0
  • HTTP+JSON -- REST endpoints

TCK auto-detects transports from your agent card.

3. Scenario Executor

Handle messageId prefixes from Gherkin scenarios:

  • tck-complete-task
  • tck-artifact-*
  • tck-input-required
  • tck-stream-*
  • ...and more
9

Building Your SUT: Step by Step

  • Read the Gherkin scenarios in scenarios/
    These define every behavior the TCK will test. Each scenario ties a messageId prefix to an expected action.
  • Implement an agent card endpoint
    Serve /.well-known/agent-card.json with your supported interfaces, capabilities, input/output modes.
  • Implement a message executor that dispatches on messageId prefix
    When the messageId starts with tck-complete-task, complete the task with "Hello from TCK", etc.
  • Wire up transport endpoints using your SDK's framework
    The SDK handles protocol serialization. Your executor focuses on business logic.
  • Run the TCK: ./run_tck.py --sut-host http://localhost:9999
    Fix failures iteratively. Start with --level must for mandatory requirements first.

Running the TCK

Basic usage

# Run all tests
./run_tck.py --sut-host http://localhost:9999

# Run only MUST requirements
./run_tck.py --sut-host http://localhost:9999 \
  --level must

# Run a single transport
./run_tck.py --sut-host http://localhost:9999 \
  --transport grpc

# Verbose with logs
./run_tck.py --sut-host http://localhost:9999 \
  --verbose-log

Iterative approach

Start with --level must to fix mandatory issues first, then --level should, then full suite.

CI integration

Use junitreport.xml for CI pipelines. Gate deployments on mandatory test results.

Reference SUTs

# a2a-java (Quarkus)
make codegen-a2a-java-sut
cd sut/a2a-java
mvn package && mvn quarkus:dev

# a2a-python
make codegen-a2a-python-sut
cd sut/a2a-python
uv sync && uv run python sut_agent.py

# Test either SUT
./run_tck.py --sut-host \
  http://localhost:9999

Summary

The TCK is a black-box test suite that validates A2A protocol conformance across gRPC, JSON-RPC, and HTTP+JSON transports.

Gherkin scenarios define SUT behaviors using messageId prefixes as in-band signals -- no side-channel API needed.

Your SDK needs: an agent card, transport endpoints, and a scenario executor that dispatches on messageId prefixes.

Run iteratively: start with MUST requirements, fix failures, then expand to SHOULD and MAY levels.

./run_tck.py --sut-host http://localhost:9999
